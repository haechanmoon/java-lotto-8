# [프리코스 3주차] 로또

## 프로젝트 소개

사용자로부터 로또 구입 금액을 입력받아 로또를 발행하고, 당첨 번호와 보너스 번호를 입력받아 당첨 통계 및 수익률을 계산하는 콘솔 애플리케이션입니다.

## 기능 요구 사항

### 간단한 로또 발매기를 구현한다.

- 로또 번호의 숫자 범위는 1~45까지이다.
- 1개의 로또를 발행할 때 중복되지 않는 6개의 숫자를 뽑는다.
- 당첨 번호 추첨 시 중복되지 않는 숫자 6개와 보너스 번호 1개를 뽑는다.
- 당첨은 1등부터 5등까지 있다. 당첨 기준과 금액은 아래와 같다.
    - 1등: 6개 번호 일치 / 2,000,000,000원
    - 2등: 5개 번호 + 보너스 번호 일치 / 30,000,000원
    - 3등: 5개 번호 일치 / 1,500,000원
    - 4등: 4개 번호 일치 / 50,000원
    - 5등: 3개 번호 일치 / 5,000원
- 로또 구입 금액을 입력하면 구입 금액에 해당하는 만큼 로또를 발행해야 한다.
- 로또 1장의 가격은 1,000원이다.
- 당첨 번호와 보너스 번호를 입력받는다.
- 사용자가 구매한 로또 번호와 당첨 번호를 비교하여 당첨 내역 및 수익률을 출력하고 로또 게임을 종료한다.
- 사용자가 잘못된 값을 입력할 경우 IllegalArgumentException을 발생시키고, "[ERROR]"로 시작하는 에러 메시지를 출력 후 그 부분부터 입력을 다시 받는다.
    - Exception이 아닌 IllegalArgumentException, IllegalStateException 등과 같은 명확한 유형을 처리한다.

## 핵심 학습 내용/고민한 점

* **TDD(테스트 주도 개발) 맛보기**: 2주차의 다짐대로 TDD에 도전했습니다. 테스트(창)를 먼저 작성하고 본 코드(방패)를 만들어 `RED` -> `GREEN` 사이클을 경험했습니다.
  `Validator`처럼 예외 처리가 많은 부분은 TDD가 코드의 안정성을 보장하는 강력한 안전망이 된다는 것을 느꼈습니다.
* **`Enum`의 적극적인 활용**: `Messages` 같은 단순 상수 모음을 넘어, `LottoRank` Enum에 일치 개수, 상금, 출력 문구 같은 데이터와,
  `valueOf()`, `getWinnings()` 같은 메서드까지 함께 캡슐화했습니다. `Enum`이 단순한 상수 관리함(or 상수 모음)이 아닌 객체임을 이해했습니다.
* **에러 시 재시도 로직 구현**: 1,2주차와 다른 요구사항인 "예외 발생 시 재입력"을 구현하기 위해, `InputView`의 각 메서드에 `while(true)`와 `try-catch`를 조합한
  패턴을 적용했습니다. `Validator`가 `IllegalArgumentException`을 던지면(throw), `InputView`가 이를 잡아서(catch) `[ERROR]` 메시지를 출력하고 루프를
  계속 도는 방식으로 책임을 분리했습니다.
* **'else 금지'와 '15라인 제한' 준수**: else금지와 15라인 제한 요구사항을 지키기 위해 노력했습니다. `else`를 피하기 위해 `if (...) { throw ... }` 또는
  `if (...) { return ... }`과 같은 패턴을 활용했습니다. '15라인 제한'을 지키기 위해 `LottoGame`의 `generateLottos`,
  `calculateStatistics`처럼 기능들을 `private` 도우미 메서드로 분리하여 가독성과 단일 책임을 높였습니다. 처음에는 15라인안에 코드를 어떻게 짜지? 라는 생각이 들었지만
  일단 기능들을 다 구현한 뒤 마지막에 리팩토링 했습니다. 1주차 엄청나게 긴 코드를 보니 코웃음이 치면서도 많이 성장했단 증거이니 뿌듯하기도 합니다.

## 어려웠던 점 및 해결과정

* **TDD와 본 코드의 균형:** TDD를 처음 시도하는 것이다보니 정말 많은 시간을 들여야만 했습니다. TDD를 모든 곳에 적용하려다가 아직 익숙치 않아 본 코드의 전체적인 흐름을 짜는 데 방해가 되었습니다.
  "TDD를 하다 0점을 맞을 수 있다"는 현실적인 고민 끝에, `Validator`, `LottoRank` 같은 로직만 일부 TDD로 먼저 구현하고, `InputView`, `LottoGame` 같은 조립 코드는
  2주차처럼 본 코드를 먼저 짰습니다. TDD를 완전히 하기엔 아직 많이 멀었던 것 같습니다. 남과 비교하지 않고 나만의 페이스를 찾으라는 피드백이 떠올랐습니다. 좀 더 강해지고 난 뒤 TDD에 뛰어들겠습니다. '
  도전'한 것에 뿌듯합니다.
* **Lotto 클래스의 역할:** 처음에는 제공된 `Lotto.java`의 `// TODO` 의도를 파악하기 어려웠습니다. 하지만 `LottoGame`의 책임을 덜어주기 위해, `Lotto`(부품)
  스스로가 자신의 상태를 검증(`validate` 강화)하고, 번호 정렬, 번호 포함 여부, 일치 개수 세기 같은 스스로 할 수 있는 일을 갖도록 기능을 추가하며 객체지향적인 설계를
  완성하려 노력했습니다.
* **AI 피드백:** 2주차에는 AI를 멘토처럼 썼다면, 3주차에는 TDD라는 새로운 도전을 함께하는 피드백 도우미로 활용했습니다. TDD를 처음 도전하다 보니 맞는 방향으로 가고 있는가를 피드백 받는 것은
  필수적이었습니다. 막힌 부분에 대해 질문하고, 제 코드의 오류를 찾아내며 피드백을 받았습니다. 30분 원칙을 지키려 노력했습니다. 무엇이든 바로바로 물어보는 것이 아닌, 일단 30분 고민해본 뒤   
  도움을 받을 수 있도록 했습니다. 덕분에 많은 공부를 할 수 있게 되었으며, 끝까지 포기하지 않고 3주차를 완주 할 수 있는 힘이 되었던 것 같습니다.
* **Enum:** `Enum` 또한 제가 처음 접했습니다. `Enum`을 활용해야 한다는 요구사항을 본 뒤 '음..이게 어디서 사용될까?'를 고민했습니다. `Enum`을 사용하기에 앞서 TDD와 마찬가지로 많은
  예제들과 기술 블로그들을 보고 공부해야했습니다. `LottoRank` 클래스가 딱 1,2,3,4,5등을 관리하기 때문에 '아! 여기서 쓰라는 힌트구나!' 라는 생각을 하게됐습니다.
  막상 `LottoRank`를 작성하니 수많은 빨간 밑줄을 마주해야 했습니다. 100점은 아니겠지만 끝까지 포기하지 않고 구현을 완성했습니다.

## 설계 과정

* **`InputView` (입력):** `while-try-catch` 패턴을 적용해 에러 시 재시도라는 3주차의 핵심 UI 로직을 전담했습니다.
* **`Validator` (검증):** `InputView`로부터 검증 책임을 분리했습니다. TDD를 통해 일부 예외 처리 방패를 구현하고, 검증과 형 변환을 통과한 깨끗한 데이터(`int`,
  `List<Integer>`)를 반환하도록 설계했습니다.
* **`LottoGame` (매니저/컨트롤러):** 2주차의 `RacingGame`처럼, 모든 객체들을 조립하고 게임의 전체 흐름(`구입 -> 발행 -> 출력 -> 당첨번호입력 -> 결과계산 -> 최종출력`)을
  관리합니다. '15라인 제한'을 지키기 위해 몇몇 로직은 `private` 도우미 메서드들에게 위임했습니다.
* **`Lotto` (도메인):** 3주차의 핵심 부품입니다. 제공된 `validate`를 강화(중복, 범위 검사)하고, `getSortedNumbers`, `countMatchingNumbers` 등 자신의
  데이터를 처리하는 기능을 추가했습니다.
* **`LottoRank` (Enum/도메인):** 3주차의 핵심 기술입니다. 1등~5등이라는 집합을 정의하고, 각 등급에 상금, 일치 개수 등의 데이터와 기능(`valueOf`)을
  캡슐화했습니다.
* **`OutputView` (출력):** `LottoGame`으로부터 계산이 끝난 데이터(`List<Lotto>`, `Map<LottoRank, Integer>`, `double yield`)를 받아,
  요구사항의 형식에 맞게 출력하는 책임만 담당했습니다. `Enum`과 `String.format`을 활용해 통계 출력을 구현했습니다.
* **`Messages` (상수):** 2주차와 동일하게, 모든 `static final` 문자열 상수를 관리하여 매직 스트링을 제거하고 유지보수성을 높였습니다.
